我们的项目由三类角色协同完成：

  • 商务负责人：负责把合适的需求接进来。
  • 方案负责人：负责把需求定义清楚，形成可实施、可验收的方案。
  • 实施负责人：负责按照确认后的方案，把系统做出来并稳定交付。
商务找到真实问题 → 方案确定做什么、怎么验收 → 实施把方案做成可用成果

一个人可以兼任多个角色，但每个项目中必须明确当前以哪个角色作决定，不能把三类职责混在一起。

负责什么

商务判断：这个客户的问题是否真实，是否值得继续投入，有没有成交和推进的可能。

主要工作：

  1. 找到潜在客户和业务场景。
  2. 了解客户为什么想做 AI。
  3. 找到使用者、项目推动人和采购决策人。
  4. 组织需求访谈和客户沟通。
  5. 判断客户是否愿意投入人员、数据、时间和预算。
  6. 方案确认后负责价格、合同、付款、周期和维护条件。
  7. 交付后负责回款、续约和新增机会。

怎么做

不要先介绍产品或承诺能力，先问四件事：客户遇到什么问题；问题影响谁；谁推动；客户愿意投入什么。

围绕最近一次真实事件追问：何时发生、谁处理、花多长时间、造成什么影响、多久发生一次、不处理有什么后果。

商务交出的不能只是“客户想做 AI 客服”，应说明：每天多少工单、哪一步耗时、谁处理、造成什么影响、想改善什么结果。

怎样算完成

  • 有具体业务场景、使用者和客户负责人。
  • 问题来自真实事件。
  • 客户愿意接受调查并提供必要样例、人员或数据。
  • 决策路径和预算状态已了解，未知项已标明。
  • 客户愿望、确认事实和我们的判断分开记录。

主要产物：商机卡、访谈记录、当前流程、需求证据包、商务条件及项目确认记录。

边界

商务可以确认客户关系、沟通计划、价格、采购和付款。不能单独承诺技术一定实现、准确率、上线日期、数据一定可接、临时功能免费增加或演示成功等于正式交付。技术效果、范围和日期须经方案与实施评估。

不把客户愿望直接当需求，不把未经评估的想法直接卖给客户。

负责什么

方案负责人回答：客户真正应该做什么，第一阶段做多大，怎样做，最后怎样判断成功。

主要工作：审计需求证据；还原真实流程；选择首个场景；定义做与不做；检查数据、系统、权限和人员；选择规则、工作流、知识库、模型或智能体；验证最大不确定性；制定业务、产品和技术指标；定义人审、异常与风险；形成实施人员能理解的任务。

怎么做

先检查能否说清：

谁，在什么场景，使用什么输入，完成什么任务，目前卡在哪里，造成什么影响，希望将哪个指标从什么状态改善到什么状态。

说不清则退回商务补充。说清后：

  1. 还原角色、触发、输入、动作、输出和异常。
  2. 选择证据充分、价值明确、数据可得、风险可控、能较快使用的小场景。
  3. 定义包含输入、处理、输出、人审、回写、异常的最小可交付方案。
  4. 同时写清做什么和不做什么。
  5. 核实数据、接口、权限及客户配合。
  6. 能用规则先用规则；步骤固定优先工作流；需要企业资料用知识检索；开放路径才考虑 Agent。
  7. 用少量真实样例验证最大不确定性，预先设定样本、方法、期限和停止条件。
  8. 指标写清基线、目标、样本、计算方法、周期、证据来源和确认人。

怎样算完成

商务、实施和客户都能看明白：解决什么、为何先做、做与不做、需要哪些条件、人／AI／系统如何分工、异常如何处理、投入多少、怎样验收、关键不确定性是否验证、实施能否估算开工。

主要产物：问题定义、目标流程、场景结论、MVD、PoC 及结果、数据系统要求、技术路线、人机边界、验收指标、一页式方案和实施任务包。

边界

方案负责人不能代替商务决定价格合同，不能代替客户确认事实，不能无证据保证效果，不能绕过实施承诺工作量和日期，不能随意扩范围或把 PoC 当正式验收。

先定义问题和边界，再选技术；先交付小而完整的业务闭环，再扩展。

负责什么

实施负责人回答：怎样把确认后的方案做出来，并保证能够运行、测试、部署和维护。

主要工作：评估工作量与依赖；拆分数据、开发、页面、测试、部署任务；准备数据、账号、接口和环境；完成规则、提示词、知识库、工作流、Agent、页面及连接；补齐人审、异常、权限、日志、监控和恢复；完成测试、试点支持、培训、部署、移交和运行维护。

怎么做

开工前检查：业务问题、做与不做、输入输出和规则、数据接口权限、测试验收标准是否明确。不完整则退回方案，不能边猜边做。

开工后依次：任务唯一主责 → 明确输入输出和检查方法 → 实测数据接口权限 → 跑主流程 → 补人审回写异常 → 固定样本测试 → 完成正常异常权限恢复测试 → 形成试点版本和说明 → 交独立质检。

怎样算完成

必需功能完成；真实数据接口实测；业务闭环跑通；缺资料不编造；失败超时有处理；高风险有人审；不能越权；结果可回写；日志监控明确；有部署恢复接手说明；阻断、数据破坏、越权问题清零；达到试点准入标准。

主要产物：实施任务清单、数据环境就绪清单、字段接口约定、可运行版本、测试记录、已知问题、部署恢复说明、操作维护说明。

边界

实施可以决定不影响业务范围的技术细节，并提出风险和估算。不能改变需求、降低验收、私下加功能、把模拟数据当真实可用、把内部测试当客户验收、未授权读写数据、自动执行资金合规不可逆动作，或把新增需求混入维护。

按确认方案建设，按约定标准测试；范围或目标有问题时退回评估。

4.1 商务 → 方案：把商机交成合格需求

商务至少交付：客户与负责人、真实事件、当前做法、问题影响、工作量、目标结果、可用样例、付费与配合意愿。

方案检查：事实是否真实、证据是否足够、是否值得进一步设计。

退回条件：只有技术想法；缺实际使用者；无真实事件；无样例；目标无法衡量。

4.2 方案 → 商务：把方案变成可成交范围

方案至少交付：问题定义、首期范围、排除项、客户配合、PoC结论、风险、实施估算和验收方法。

商务检查：对外说法是否准确；合同范围、费用、周期和付款节点是否能明确。

4.3 方案 → 实施：把方案交成可开工任务

方案至少交付：目标流程、角色权限、输入输出、数据知识、系统接口、人机边界、异常处理、测试集和验收指标。

实施检查：能否估算、拆任务、取得依赖、建设和测试。

退回条件：需要猜需求；数据和接口未确认；异常和人审缺失；验收不可执行。

4.4 实施 → 方案／商务：把系统交成可验收结果

实施至少交付：可运行版本、测试报告、试用数据、已知问题、部署回滚说明、操作维护手册。

方案检查：是否符合问题、范围和验收标准。商务根据确认结果推进客户验收、回款和后续合作。

AI 落地商务与需求挖掘实战手册

适用对象：不熟悉 AI、但需要找客户、谈需求、判断项目并移交方案团队的商务人员。

找到合适客户 → 听懂真实问题 → 判断业务价值 → 判断落地条件 → 切出首期场景 → 推进成交 → 完整移交

商务的核心任务不是介绍 AI，也不是替技术人员设计系统，而是完成三件事：

  1. 找到值得解决的问题。
  2. 判断客户是否真的愿意推动。
  3. 把经过初筛、有证据的需求交给方案负责人。

最终分工参见：企业AI改造项目三类核心角色说明。商务完成需求初筛后，下一步参见：AI落地方案设计实战手册。跨岗位交接参见：商务-方案-实施协作与交互关系图。

1. 客户购买的是结果

客户通常不关心模型、提示词、RAG 或 Agent 的技术细节。他们真正愿意付费的结果主要有四类：

客户价值常见表现可验证指标
减少耗时少查资料、少录入、少复制、少重复回复单次处理时间、总工时、响应时间
降低错误统一口径、减少遗漏、增加检查错误率、退回率、投诉率
沉淀经验把老员工经验转成团队能力知识覆盖率、新人上手时间、复用次数
扩大产能同样人力处理更多业务人均处理量、客户承载量、交付周期

因此，商务不要说：

“我们可以给您做一个智能体。”

而要说：

“我们先找出团队最耗时、最容易出错的一步，再验证 AI 能否减少处理时间和错误；验证有效后，再交付可以实际使用的系统。”

2. 三条基本原则

  1. 先找业务问题，再选择技术。
  2. 先验证一个小闭环，再扩大范围。
  3. 先约定验收证据，再讨论预期效果。
商务第一原则

客户说“想做 AI”只是意愿，不是需求。只有当使用者、场景、问题、影响和目标结果基本明确时，才形成可评估的需求。

1. 优先客户的六个信号

  • 存在每天或每周反复发生的工作。
  • 员工大量查找、整理、录入、复制或回复信息。
  • 业务明显依赖少数老员工或专家经验。
  • 资料散落在文档、表格、聊天记录和不同系统中。
  • 响应慢、错误或遗漏会带来成本、投诉或收入损失。
  • 有明确负责人愿意投入人员、资料、时间和预算。

2. 暂时不应优先投入的客户

  • 只想“了解一下 AI”，没有具体问题。
  • 只有兴趣，没有负责人、时间或预算。
  • 不愿让实际使用者参与访谈。
  • 不愿提供任何样例、资料或测试条件。
  • 一开始就要求改造全部业务。
  • 要求百分之百准确或完全替代员工。

3. 第一轮沟通的目标

第一次沟通不是立即成交，而是判断是否值得进入正式访谈。至少确认：

  • 问题是否真实发生。
  • 问题是否值得解决。
  • 客户是否愿意配合。
  • 谁能够推动和决定。

推荐开场：

“先不讨论具体 AI 产品。您团队目前最耗时间、最重复，或者最容易出错的一项工作是什么？”

4.1 不听概念，追最近一次真实事件

客户说“客服效率低”“知识太乱”时，不要马上记录为需求。请他描述最近一次真实发生的事情：

“最近一次出现这个问题是什么时候？谁接到任务？第一步做了什么？中间查了哪些资料？在哪里卡住？最后用了多久？”

真实事件能暴露实际流程、隐性动作、例外情况和真正损失。

4.2 六组必问问题

A. 谁在做

  • 谁是实际使用者？
  • 一共有多少人做这项工作？
  • 谁对结果负责？
  • 谁能推动项目，谁决定预算？

B. 现在怎么做

  • 什么事情会触发这项工作？
  • 从开始到结束依次经过哪些步骤？
  • 每一步使用什么资料或系统？
  • 最终输出给谁，进入哪个下一环节？

C. 工作量有多大

  • 每天、每周或每月发生多少次？
  • 单次通常耗时多久？
  • 高峰期是多少？
  • 有多少人力长期投入？

D. 真正痛在哪里

  • 哪一步最耗时间？
  • 哪一步最容易出错或遗漏？
  • 哪一步最依赖老员工判断？
  • 哪一步经常返工、等待或反复沟通？

E. 不解决有什么影响

  • 浪费多少工时或成本？
  • 是否影响客户响应、成交、交付或回款？
  • 是否造成投诉、退货、罚款或风险？
  • 问题继续一年，影响会有多大？

F. 做好以后怎样算成功

  • 希望哪个业务指标发生变化？
  • 当前基线是多少？
  • 期望改善到什么程度？
  • 谁确认结果，依据什么数据确认？

4.3 把“想要一个 AI”翻译成业务需求

使用这个句式：

某类使用者，在某个具体场景中，需要根据某些输入完成某项任务；现在因为某个卡点造成某种影响，希望把某项指标从当前状态改善到目标状态。

例如，客户原话是：

“我们想做一个 AI 客服。”

翻译后：

售后人员收到文本工单后，需要判断问题类型、查找企业资料并准备回复。目前分类和查资料占用大量时间，且回复口径不一致。希望缩短首次响应时间，同时降低错误回复和不合理转人工。
需求不合格的典型表现

“做个知识库”“做个智能体”“让 AI 帮销售”都只是方案或想法。必须继续追问：谁用、何时用、输入什么、完成什么、现在有什么损失、怎样算有效。

4.4 访谈现场的记录规则

把记录分成三类：

类型含义示例
已确认事实客户能提供事件、数据或样例每天约 200 条工单
客户判断客户的感受或估计，尚未核实大约一半问题是重复咨询
待验证假设我方暂时推测AI 分类可能减少人工处理时间

不要把三类内容混写，否则后续容易把推测当成承诺。

5.1 六维价值评分

每项按 1～5 分评估，并写一句依据。没有证据时不能凭感觉给高分。

维度1 分表现5 分表现
痛点强度只是觉得麻烦持续造成成本、投诉、风险或收入损失

价值大小改善后影响很小能显著提效、降错、增收或沉淀经验

建议结论：

  • 24～30 分：优先进入方案评估。
  • 18～23 分：先补证据或缩小场景。
  • 低于 18 分：暂缓投入。

分数只是辅助，以下任一情况出现时应暂停：没有负责人、没有验证条件、没有付费意愿、风险无法控制。

5.2 一个简单的商业价值估算

至少估算一次，避免只谈感受：

年度可释放工时 = 每次可节省时间 × 年处理次数 × 涉及人数

还可以补充：

  • 错误减少可能避免的损失。
  • 响应变快可能提高的成交或续约。
  • 经验沉淀可能缩短的新人培训时间。
  • 自动化后新增的业务承载量。

这里计算的是机会规模，不是效果承诺。最终效果必须通过真实试点验证。

商务不需要会开发，但必须完成以下初筛。

6.1 可行性七问

检查项必须问清楚的内容不清楚时怎么办
使用者谁会实际使用找到实际使用者访谈
输入系统会收到什么索要真实脱敏样例

数据资料依据从哪里来盘点文档、表格、数据库和历史记录

风险边界出错会造成什么后果增加人审、权限、转人工或停止自动执行

6.2 快速结论：需求清、数据有、风险可控

三项分别打 1～5 分：

  1. 需求清：场景、输入、输出和目标是否说得清。
  2. 数据有：是否有足够且可合法使用的资料和样例。
  3. 风险可控：出错是否可发现、可拦截、可转人工、可恢复。

判断规则：

  • 三项都 ≥4：可以设计小范围 PoC。
  • 有一项为 3：补条件后再做。
  • 任一项 ≤2：暂不承诺实施。

6.3 商务必须升级给方案负责人的情况

  • 需要连接客户现有业务系统或写入生产数据。
  • 涉及个人隐私、商业机密或敏感数据。
  • 涉及付款、审批、合同、医疗、法律或安全判断。
  • 客户要求明确准确率、并发量、上线周期或替代人数。
  • 数据质量、接口权限或部署方式不确定。
  • 错误结果可能带来较大损失。
  • 客户要求一次覆盖多个部门和流程。

商务可以说“我们进入评估”，不能直接说“肯定能做”。

7.1 首期场景的选择标准

优先选择：

  • 高频发生。
  • 痛点明显。
  • 输入和输出清楚。
  • 有真实样例和业务专家。
  • 出错可以人工拦截。
  • 能在小范围、短周期内看到结果。

首期不要选择：跨多个部门、规则持续变化、必须完全自动、失败代价很高、短期无法取得数据的场景。

7.2 一个完整的小闭环

首期方案至少说清：

谁使用 → 什么触发 → 输入什么 → AI／规则做什么 → 输出什么 → 谁确认 → 结果写到哪里 → 异常怎么办

例如：

售后人员收到工单后，系统识别问题类型，检索批准的企业知识并生成回复建议；售后人员确认后发送。投诉、退款、无依据和低置信度问题自动转人工，处理结果回写用于统计和优化。

7.3 首期范围必须同时写“做什么”和“不做什么”

首期做首期不做
文本工单分类语音、图片等全部渠道同时接入
企业知识检索AI 自行编写无来源答案
回复建议无人审核直接对外发送
高风险转人工自动退款、赔付或审批
结果记录一次替换全部售后系统

清楚的“不做”能保护报价、周期和交付质量。

推荐按四个阶段成交：

  1. 诊断：明确问题、价值、条件和优先级。
  2. 小范围验证：用真实脱敏样例验证最大不确定性。
  3. 正式实施：完成可使用系统、测试、部署和培训。
  4. 运营优化：根据真实使用数据持续更新知识、流程和指标。

成交前必须让客户确认：

  • 解决哪个具体问题。
  • 首期包含什么、不包含什么。
  • 客户提供哪些人员、资料、权限和环境。
  • 哪些情况由人工处理。
  • 使用什么数据和指标验收。
  • 周期、费用、付款节点和变更规则。

商务可以承诺

  • 安排调研和评估。
  • 按双方确认的范围组织验证。
  • 提供明确的交付物和验收方法。
  • 用真实数据说明试点结果。

商务不能单独承诺

  • 技术一定能够实现。
  • 准确率一定达到某个数字。
  • 一定替代多少员工。
  • 未经评估的上线时间和工作量。
  • 演示效果等同于正式交付效果。
  • 临时增加的功能免费完成。

不能只发一句“客户想做 AI 客服”。一份合格的需求移交包至少包含：

  1. 客户和项目负责人信息。
  2. 最近一次真实问题的完整描述。
  3. 当前流程及参与角色。
  4. 频率、耗时、错误和损失证据。
  5. 客户希望改善的业务指标。
  6. 可提供的数据、资料和真实脱敏样例。
  7. 涉及的系统、接口、权限和敏感信息。
  8. 客户预算、决策人、时间要求和配合意愿。
  9. 已知风险、未知项和待验证假设。
  10. 商务建议的首期场景，但不能替代方案结论。

方案负责人收到后给出三种结论之一：

  • 通过：信息足够，可以进入方案设计。
  • 退回补充：写清缺什么、谁补、什么时候补。
  • 暂停：说明价值、数据、预算、权限或风险原因。
合格移交标准

方案负责人不需要重新从头问客户，就能理解谁遇到什么问题、问题有多大、有哪些证据、客户能提供什么，以及下一步最需要验证什么。

第一步：初筛客户

  • 是否有真实、高频、持续造成影响的问题？
  • 是否有明确负责人和付费意愿？
  • 是否愿意安排实际使用者参加访谈？

全部基本满足，再约正式访谈。

第二步：完成访谈

  • 追一件最近发生的真实事件。
  • 还原触发、角色、步骤、资料、输出和异常。
  • 问出频率、耗时、错误和业务影响。
  • 确认客户想改善的指标。
  • 索要真实脱敏样例。

第三步：完成判断

  • 用六维评分判断值不值得做。
  • 用“需求清、数据有、风险可控”判断能不能验证。
  • 高风险或系统连接问题交方案负责人评估。

第四步：定义小切口

  • 只选一个高价值场景。
  • 写清使用者、输入、处理、输出、人审和异常。
  • 写清首期做什么、不做什么。

第五步：推进成交和移交

  • 优先成交诊断或小范围验证。
  • 确认范围、配合条件、验收、周期和费用。
  • 整理完整需求证据包，移交方案负责人。

这套内容可拆成七节内部培训：

  1. AI 企业落地到底在卖什么。
  2. 什么样的客户值得找。
  3. 怎样完成一次需求访谈。
  4. 怎样判断需求值不值得做。
  5. 怎样判断需求能不能做。
  6. 怎样切出最小验证项目。
  7. 怎样成交并移交方案和实施团队。

每节统一使用：

概念讲解 → 判断标准 → 操作步骤 → 提问话术 → 正反案例 → 表单填写 → 现场演练

学员结业时应能独立完成四份成果：

  • 《客户初筛与商机卡》
  • 《业务问题访谈记录》
  • 《需求价值与可行性评分表》
  • 《首期验证项目说明书》

如果四份成果仍说不清“谁、在什么场景、遇到什么问题、影响多大、怎样验证、客户提供什么”，说明需求还没有挖清楚，不能直接进入实施。

方案负责人承接商务筛选后的需求，回答五个问题：

  1. 客户真正要解决的业务问题是什么？
  2. 这个问题是否值得用 AI 解决？
  3. 第一阶段应该做多大？
  4. 人、AI 和业务系统分别负责什么？
  5. 做到什么程度才算交付成功？
核心任务：把业务问题转化成范围清楚、能够实施、可以验收的项目方案。

方案负责人不是“写方案书的人”，而是项目定义者。方案含糊，后续就容易出现报价失真、开发返工、客户预期失控和验收争议。

必须守住的四条原则

  1. 先定义问题，再选择技术。
  2. 先完成小而完整的业务闭环，再扩大范围。
  3. 先验证最大不确定性，再承诺正式实施。
  4. 先确定验收证据，再讨论目标效果。

不属于方案负责人的决定

  • 不代替商务决定报价、合同和付款。
  • 不代替客户确认未经核实的事实。
  • 不绕过实施负责人承诺工作量和上线时间。
  • 不直接把客户随口提出的功能清单当方案。
  • 不在缺少证据时承诺准确率和业务效果。

11.1 用普通话解释 PoC

PoC 是英文 Proof of Concept 的缩写，中文通常叫“概念验证”或“可行性验证”。

这个名字容易让人困惑，可以直接把它理解成：

正式投入大量时间和费用之前，先用少量真实材料做一次小实验，验证最关键的事情到底能不能成立。

例如，客户想做“售后 AI 助手”，现在最大的疑问是：AI能否根据企业资料给出有依据的回复。PoC不需要先做完整客服系统，而是取一批真实脱敏工单和企业资料，测试回复质量，回答“这条路能不能走”。

11.2 为什么不能直接开始做正式系统

AI项目常有几类不确定性：

  • 客户资料可能不足以支持回答。
  • 历史数据可能太乱或缺少标准答案。
  • AI输出可能看起来流畅，但业务上不能使用。
  • 客户系统可能没有可用接口。
  • 实际使用者可能不愿采用新的操作方式。

如果不先验证，团队可能做完页面、账号和接口后，才发现核心能力不成立。PoC的作用是用较低成本提前暴露这种问题。

11.3 PoC 与几个常见概念的区别

概念主要目的是否可正式使用关注重点
演示 Demo展示一个想法或效果通常不可以看起来是否直观
PoC验证关键能力能否成立通常不可以最大不确定性是否被证明
最小可交付系统让小范围用户完成真实工作可以业务闭环是否跑通
试用／试点在真实环境观察使用效果可以，小范围用户是否采用、指标是否改善
正式系统长期稳定支持业务可以稳定、安全、维护和规模化
最容易混淆的一点

演示成功只能说明“可以展示”，PoC通过说明“关键能力在限定条件下成立”，只有完成系统建设、测试和真实试用，才说明“可以交付使用”。

11.4 什么情况下需要 PoC

  • AI识别、分类或生成质量尚不确定。
  • 企业资料能否支持知识问答尚不确定。
  • 数据质量和样本数量尚不确定。
  • 关键接口能否连接尚不确定。
  • 客户提出的目标值缺少证据。
  • 正式实施成本较高，走错路线代价较大。

如果技术和流程都成熟、数据条件清楚、风险很低，可以不单独设PoC阶段，但仍需保留小范围测试。

11.5 PoC结束后只能有三种结论

  1. 通过：关键能力达到预设标准，可以进入正式方案。
  2. 调整后再验证：方向有希望，但数据、规则或范围需要调整。
  3. 不通过：关键假设不成立，停止或更换解决方法。

PoC不通过不等于项目失败。用小成本证明一条路线不可行，本身就在帮助客户避免更大的错误投入。

12.1 先找最大的不确定性

例如：AI能否识别核心输入；企业资料能否支持回答；输出是否能被员工采用；关键接口是否可连接。

一次PoC尽量只验证一到两个关键问题，不能借PoC名义建设完整系统。

12.3 示例

12.4 防止PoC失真

  • 包含正常、困难、无资料和高风险样本。
  • 测试前确定标准，不能看到结果后再改。

  • PoC结果不能直接当生产验收结论。

“功能做出来”不等于完成交付

一个真正可交付的系统还必须具备：

  • 真实数据和接口经过测试。
  • 错误、超时和资料不足时有处理办法。
  • 高风险动作有人工确认。
  • 用户权限和数据范围受控。
  • 处理过程有记录，可以追踪问题。
  • 有部署、恢复、操作和维护说明。
  • 客户使用者经过试用并能够完成工作。

实施负责人的边界

  • 可以决定不改变业务范围的技术实现细节。
  • 可以对工期、依赖、风险和成本提出专业判断。
  • 不能私自改变业务目标、范围和验收标准。
  • 不能把新增需求直接混入当前开发。
  • 不能用模拟数据冒充真实可用。
  • 不能绕过授权读取或写入客户数据。
  • 不能把内部测试通过说成客户已经验收。

5.1 环境是什么

可以把“环境”理解为系统运行的一套独立场地，包括程序、配置、账号、数据库和接口。

环境用途数据要求
开发环境实施人员建设和调试优先使用模拟或脱敏数据
测试环境完整测试和客户确认使用受控的测试数据
生产环境支持客户真实业务使用正式数据，严格控制权限

不同环境应尽量隔离，不能在调试时误操作正式数据。

5.2 部署是什么

部署就是把已经完成的系统安装、配置并启动到指定环境，让目标用户能够访问和使用。

5.3 版本是什么

版本是某一时点系统内容和配置的明确快照。每次重要修改都应记录：版本号、日期、修改内容、修改人、测试结果和恢复方式。

基本规则

能说清“哪个版本、部署在哪里、使用哪份数据、由谁修改”，问题发生时才有可能快速定位和恢复。

AI系统的效果很大程度取决于输入数据和知识。模型强不代表脏数据会自动变正确。

6.1 数据准备八步

  1. 盘点：有哪些数据、文档、表格和历史记录。
  2. 确认权限：谁拥有，允许用于什么范围。
  3. 脱敏：删除或替换姓名、电话、账号等敏感字段。
  4. 清洗：修正格式、乱码、空值和明显错误。
  5. 去重：识别重复记录和重复文档。
  6. 分类：按业务、产品、时间和权限组织。
  7. 标注：补充标准答案、标签或处理结果。
  8. 版本化：记录来源、时间、责任人和变更。

6.2 数据清单模板

6.3 数据就绪标准

  • 来源明确且获得授权。
  • 字段和格式可以读取。
  • 敏感内容按要求处理。
  • 核心样本数量足够。
  • 错误、缺失和冲突已有记录。
  • 数据能够代表真实业务，而不只是成功样例。
  • 客户业务负责人确认可用于测试。

7.1 用普通话解释

企业 AI 知识库不是一个普通文件夹，也不是把文件上传后就结束。它是一套让 AI 能够从企业批准资料中找到相关内容、给出有依据回答并能追溯来源的机制。

知识库的价值：让 AI 尽量依据企业自己的知识工作，而不是凭模型记忆猜答案。

7.2 知识库不能自动解决什么

  • 原始资料本身错误或过期。
  • 多份制度相互冲突。
  • 业务规则没有写下来。
  • 实时库存、订单状态等动态数据。
  • 需要精确计算或执行操作的任务。

这些问题需要业务确认、系统查询、规则计算或工具调用配合。

8.1 建设流程

资料盘点 → 内容筛选 → 清洗结构化 → 合理切分 → 补充标签 → 设置权限 → 导入索引 → 检索测试 → 回答测试 → 建立更新机制

8.2 每份知识至少记录

  • 标题和内容。
  • 来源文件。
  • 适用产品、部门或客户类型。
  • 生效和失效时间。
  • 内容负责人。
  • 权限范围。
  • 版本号。

8.3 测试三层效果

  1. 找得到：正确资料能否进入候选结果。
  2. 找得准：排在前面的是否真正相关。
  3. 答得对：回答是否忠于资料并带有可追溯依据。

8.4 必测情况

  • 有明确答案的问题。
  • 表达不同但含义相同的问题。
  • 跨多份资料才能回答的问题。
  • 没有答案的问题。
  • 多份资料冲突的问题。
  • 用户无权查看的问题。
  • 旧版资料已经失效的问题。

8.5 完成标准

  • 核心问题能检索到正确依据。
  • 答案能够显示或记录来源。
  • 无依据时不编造，转人工或明确告知。
  • 权限隔离经过测试。
  • 内容更新、删除和重新测试有负责人。

阶段产物：知识目录、清洗记录、元数据说明、权限表、版本记录、检索测试报告、更新SOP。

工作流可以理解为一条预先设计好的数字流水线：每一步做什么、使用什么数据、满足什么条件走哪条分支，都提前定义清楚。

例如：

工单进入 → 检查字段 → 识别类型 → 检索知识 → 生成建议 → 人工确认 → 写回记录

工作流适合步骤相对固定、需要稳定重复执行的任务。它的价值是过程清楚、容易检查、容易定位错误。

10.1 工作流必须包含

  • 触发方式。
  • 输入字段和校验。
  • 规则判断。
  • AI处理节点。
  • 知识检索。
  • 外部工具或系统调用。
  • 人工审核。
  • 结果输出和回写。
  • 异常分支。
  • 超时、重试和停止条件。
  • 日志记录。

10.2 建设顺序

  1. 先用少量样本跑通最短主流程。
  2. 固定每个节点的输入输出。
  3. 加入业务规则和知识依据。
  4. 补齐人工审核和转人工。
  5. 增加缺字段、超时和接口失败分支。
  6. 写入日志并记录每步结果。
  7. 使用固定测试集重复测试。
  8. 再连接正式页面和业务系统。

10.4 完成标准

  • 主流程端到端跑通。
  • 每一步输入输出可追踪。
  • 缺少资料时不生成假答案。
  • 失败不会无限重试或重复执行。
  • 高风险结果进入人工审核。
  • 最终结果能够回写或保存。

智能体通常指能够根据目标和当前情况，自主选择下一步动作或工具的 AI 程序。

工作流像固定路线的公交车；智能体更像知道目标后自己选择路线的司机。灵活性更高，也更需要权限、步数和停止条件。

什么时候才需要智能体

  • 任务路径无法提前完全固定。
  • 需要根据上下文选择不同工具。
  • 需要多步查找、分析和执行。
  • 每个工具权限都能明确限制。
  • 出错时可以停止并人工接管。

步骤固定的任务优先用工作流，不必为了显得先进而使用智能体。

必须定义：

  • 目标和完成条件。
  • 可使用的工具。
  • 每个工具的权限。
  • 禁止执行的动作。
  • 最大执行步数和时间。
  • 需要人工确认的节点。
  • 失败、循环和无结果时怎样停止。
  • 操作过程怎样记录。

订单查询指定订单状态无有合法订单号不需要查询失败转人工

高风险禁区

未经明确授权和人工确认，智能体不应自动进行付款、退款、删除、审批、合同确认、对外发布和生产控制等不可逆动作。

API可以理解为两个系统之间约定好的“办事窗口”。一个系统按规定提交信息，另一个系统返回查询结果或执行动作。

例如，AI需要回答订单是否发货，不能自己猜，需要通过订单系统API查询真实状态。

系统连接的风险通常高于单独生成文本，因为它可能读取敏感数据或改变业务状态。

14.1 连接前必须确认

  • 接口文档和技术联系人。
  • 测试环境和测试账号。
  • 允许读取和写入的范围。
  • 字段含义、格式和必填规则。
  • 身份验证和权限有效期。
  • 调用频率、并发和费用限制。
  • 超时、重试和错误码。
  • 重复请求如何避免重复执行。
  • 写入失败如何回滚。
  • 日志和审计怎样保留。

14.2 什么是“重复执行保护”

网络失败时系统可能重试。如果第一次实际成功但返回结果丢失，第二次重试可能重复创建订单或重复发送通知。因此必须使用唯一业务编号、状态检查等方式保证同一任务不会被执行两次。

14.3 测试顺序

测试环境只读查询 → 单条测试写入 → 错误输入 → 超时与重试 → 重复请求 → 权限边界 → 批量压力 → 小范围生产灰度

14.4 完成标准

  • 接口通过真实测试，不只依据文档判断。
  • 字段映射获得双方确认。
  • 最小权限生效。
  • 超时、重试、重复和回滚经过测试。
  • 所有写入动作可追踪到操作者和请求。

提示词可以理解为给 AI 的任务说明书。它需要明确任务、依据、步骤、边界和输出格式，而不是一句“你是一个专业助手”。

15.1 提示词应包含

  • 角色和任务目标。
  • 允许使用的知识依据。
  • 输入字段及含义。
  • 判断步骤和业务规则。
  • 输出格式。
  • 必须拒绝或转人工的情况。
  • 正确示例和错误示例。

15.2 版本管理

记录：提示词版本、模型版本、参数、知识版本、修改原因、测试集结果、修改人和上线时间。

任何模型、提示词、知识或关键规则变化后，都要重新运行固定测试集。

16.1 四种处理结果

  1. 自动通过：低风险且达到确定条件。
  2. 人工确认：AI给出建议，由人批准。
  3. 转专业人员：需要特定经验或权限。
  4. 拒绝执行：缺少授权、依据或风险过高。

16.2 人工审核要回答

  • 谁审核。
  • 在哪里审核。
  • 审核哪些内容。
  • 多久内完成。
  • 修改结果是否记录。
  • 拒绝后如何处理。
  • 审核人不在线怎么办。

16.3 必须人工确认的常见事项

  • 付款、退款和赔付。
  • 合同、法律和医疗结论。
  • 人事决定和生产控制。
  • 删除重要数据。
  • 对外发布和高影响客户回复。
  • 涉及敏感信息的传输。

  • 日志：系统做过什么的详细记录，用于查错和追责。
  • 监控：持续观察系统是否正常、速度和成本是否异常。
  • 告警：发现重要异常时主动通知负责人。

至少记录

  • 请求时间、使用者和任务编号。
  • 输入来源和必要字段，不随意记录敏感原文。
  • 使用的模型、提示词和知识版本。
  • 每个关键节点结果和耗时。
  • 人工修改、转人工和最终结果。
  • 接口错误、重试和恢复过程。

重点监控

  • 成功率和失败率。
  • 响应时间。
  • 转人工率。
  • 无答案和低置信度比例。
  • 单次调用成本。
  • 异常增长和接口不可用。

22.1 灰度上线

灰度上线是先让少量用户或少量业务使用新系统，观察稳定后再逐步扩大。它能降低一次性全面上线的风险。

22.2 回滚

回滚是新版本出现严重问题时，快速恢复到上一个可用版本或原业务流程。

上线前必须回答：如果失败，怎样停止、怎样恢复、数据怎样处理、谁做决定。

先讲清 PoC

PoC 是概念验证：用最小范围证明核心链路能不能产生业务价值。它不是完整系统，也不是免费完成全部需求。本项目先验证选定设备的数据能否稳定读取、能否发现一类值得处理的异常，以及结果能否直接送到维修人员手中。

关键方案判断

历史故障标签不足时，不承诺“精确预测设备何时损坏”。第一阶段将目标改为发现偏离正常状态的异常，并让维修人员更早核查，使目标可测试、可解释、可验收。

最小业务闭环

读取设备数据→形成设备状态→结合基线和知识判断异常→生成维修工单→分级通知→人工处理并反馈→优化规则与知识

PoC 必须固定的五件事

  • 对象：限定设备、产线或故障类型。
  • 输入：数据来源、频率、质量和权限。
  • 输出：异常信息必须包含的业务字段。
  • 动作：谁收到、多久处理、怎样反馈。
  • 成功标准：用什么样本、周期和口径判断继续或停止。

实施顺序

  1. 先打通并监控数据链路。
  2. 用可解释的业务规则和设备基线建立初版判断。
  3. 把异常转成维修人员可直接执行的工单。
  4. 按风险、人员和频率接入通知，避免消息轰炸。
  5. 保留有效、误报、漏报和已处理反馈入口。
保密边界

Agent 的职责和协作关系可以说明；具体 Prompt、阈值、字段、接口、账号、消息策略和部署结构不得公开。

初版系统的误报一度超过 30%。如果告警太多，一线人员会逐渐忽略系统，因此试运行阶段的重点是让“有用提醒”与团队处理能力匹配。

  1. 逐条标记有效、无效、信息不足或无需处理。
  2. 按正常工况变化、设备个体差异、数据质量和规则冲突归类误报。
  3. 优先修正高频且最影响信任的误报类型。
  4. 为不同设备建立各自基线，避免一套固定标准覆盖全部设备。
  5. 合并重复告警，限制频率，并按风险设置不同送达方式。
  6. 每次修改都用保留样本回测，防止减少误报的同时增加漏报。

稳定运行后，公开口径下的误报率控制在约 10%—15%，进入一线可持续使用区间。

验收检查

  • 数据、判断、工单、通知和反馈链路完整。
  • 指标按事先冻结的设备、样本、周期和计算口径得出。
  • 数据中断、重复告警、通知失败和人工接管经过测试。
  • 高风险动作保留人工确认，系统不替代现场安全决策。
  • 维修人员能够查看、处理、反馈和关闭任务。
  • 规则、知识和版本变更可追溯、可恢复。

  1. 从损失和流程出发：客户购买的是更早发现、更快处理和更少停机。
  2. 先找专家，再谈智能：缺少标签时，现场专家是第一版判断能力的关键。
  3. 调整不可验证的目标：数据不足时，把精确预测改为异常发现和处置闭环。
  4. 让输出触发动作：告警进入工单、通知、处理和反馈后，AI 才真正进入业务。

要调查的人

  • 决策者：为什么现在想做，愿意投入什么。
  • 售后负责人：工单量、人员安排、服务指标和投诉。
  • 一线客服：最近一次工单怎样处理，哪些步骤最耗时。
  • IT／数据负责人：工单来源、知识资料、接口、权限和部署条件。

访谈重点

  1. 最近一次安装指导、故障排查、配件订购工单是怎样处理的？
  2. 分类、查资料、拟回复、确认和发送分别花多久？
  3. 哪些问题允许自动回复，哪些必须由工程师判断？
  4. 什么情况最容易答错、漏单或引发投诉？
  5. 现有工单、FAQ、产品说明和处理结果能否提供脱敏样例？
  6. 谁推动、谁验收、预算和采购怎么走？

商务交接物

商机卡、访谈记录、当前流程、样例清单、联系人、预算状态。案例中的背景用于理解方法；面对具体客户时仍需重新调查，并以客户确认的事实作为方案依据。

问题定义

售后客服收到工单后，需要人工识别类别、查找资料并生成初步回复。高频重复问题占用大量时间，使响应延迟；目标是让系统辅助完成低风险、重复工单的分类和常见问答，把复杂、高风险问题交给人。

最小业务闭环

收到工单→读取工单内容→规则与模型分类→置信度和风险→转人工队列→检索已批准知识→找到可靠依据?→生成带依据的拟回复→按约定自动发送或人工确认→记录结果与反馈

做与不做

做：文本工单接入、类别识别、FAQ 检索、拟回复、人工转接、处理记录、基础统计。

不做：电话语音、个人微信直连、退款审批、远程诊断后直接给维修方案、无人监督的自主 Agent、全量系统改造。

路线判断

该任务步骤固定，关键风险可写成规则。因此先使用工作流，不以自主 Agent 起步：

  • 规则节点识别投诉、退款、隐私和高风险关键词。
  • 模型节点完成文本分类与拟回复。
  • 知识检索只读取经客户批准的 FAQ、说明书和售后政策。
  • 工具负责读取和回写工单；模型本身不直接操作系统。
  • 人工节点处理高风险、低置信和无依据问题。

PoC 计划

  • 周期建议：2—4 周。
  • 样本：先用脱敏历史工单离线验证，再选少量真实工单受控试点。
  • 成功：达到双方事先确认的业务指标，并且高风险规则、人工转接和日志可用。
  • 停止：数据不可用、知识资料无负责人、重大安全风险或关键指标明显达不到时暂停。
  • ROI：按节省工时、减少漏错、平台模型费、开发陪跑及客户内部投入重新测算。

很多企业提出的第一句话是“我想做一个 AI 客服”，但这还不是可以交付的需求。本案例是一家装备制造企业，每天有大量售后工单，一线人员把很多时间花在分类、查资料和初步回复上。

我们没有从全自动客服开始，而是先选“文本工单分类＋常见问答”这个小闭环。系统识别类别后，只在高置信、低风险且能找到可靠资料时生成回复；投诉、退款、低置信和无资料问题全部转人工。

方案用小批量脱敏工单做 PoC，提前约定解决率、响应时间、转人工和安全指标。
