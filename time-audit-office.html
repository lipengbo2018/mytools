01 · WHY

它解决的不是“记事”，而是跨端失控。

当任务在对话、资料库、手机和云端之间流动时，真正难的是：谁是准的、怎么同步、错了怎么回退、今天的改动会不会明天消失。

01 / 数据分散

规划在一个地方，执行在另一个地方

任务有了，但上下文、截止日期和实际工时分散在不同端。

02 / 口径不一

“待办”和“进行中”各说各话

如果状态、逾期规则和字段含义不统一，跨端统计就会打架。

03 / 同步不安全

一次空快照，就可能覆盖整份数据

同步前必须识别“未完成数为 0”到底是正常，还是读取失败。

04 / 改动丢失

手机做完了，晚上却没有回写

手机端白天改动只留本地，需要明确的回写通道才能形成闭环。

产品的核心判断：云端负责“唯一”，手机负责“现场”，人工负责“授权与回写”。简单的单向主干，配合可控的人工支线
02 · ARCHITECTURE

三层系统，
一个数据中枢

不是双向自由合并，而是把职责切开：WorkBuddy 负责规划，小程序负责执行，云端快照负责让两端对上同一份数据。

04 · COMMANDS

三条口令，
对应三种动作

把复杂的脚本与数据处理，压缩成可记忆、可审计的自然语言入口。

口令一 · 推送

“同步到小程序”

筛选进行中 + 已推迟 → b2a 转换 → 服务端写入 → 回读核对。

WorkBuddy → 云端快照 → 手机下载
口令二 · 合并

“从小程序同步”

拉取全部任务，生成全字段合并计划：新增插入，有值覆盖，空值保留。

手机云端 → a2b → WorkBuddy 资料库
口令三 · 喂 JSON

直接发一份 JSON

按 ID 匹配，只更新状态，必要时补实际完成时间；未匹配跳过。

JSON → ID 匹配 → 状态回写
统一口径：4 态状态机 = 进行中 / 已完成 / 已推迟 / 已取消；逾期是跨状态标签，截止当天不算逾期，次日起才算。
05 · DAILY LOOP

一天怎么用？
四个动作形成闭环

系统不要求你一直维护数据，只在关键节点做一次明确动作：早上推、出门下、白天做、晚上回。

早上 · 推

对 WorkBuddy 说“同步到小程序”，把未完成任务推到云端。

出门前 · 下

打开 KitBox，点“下载云端”，整份快照落到手机。

白天 · 做

在手机计时、标完成、调整任务；改动只留本地。

晚上 · 回

在 WorkBuddy 更新状态，或用口令二 / JSON 做人工回写。

06 · SAFETY

真正的产品力，
藏在不允许发生的事里

时间系统最怕“看起来同步成功，实际上数据被覆盖”。因此安全闸不是附加功能，而是主流程的一部分。

内置安全闸

  • 口令一未完成数为 0 或读表失败：立即终止，绝不用空快照覆盖云端。
  • 口令一属于覆盖写，方向不明时先确认。
  • 口令二 / 三只动允许字段，绝不删记录，未匹配绝不新建。
  • 删除只在 WorkBuddy 端执行；手机端删除重新下载后会按云端数据恢复，系统不使用墓碑机制。
  • 所有同步必须回读验证，不只看写入返回码。
  • 手机“下载云端”只读，不上传任何本地数据；当前微信账号必须匹配运行时 openid，否则提示没有当前账号数据。
  • 空结束时间视为长期待办；旧名“待办”统一归并为“进行中”。

最终边界

云端负责唯一，手机负责现场，人工负责授权与回写。

同步靠 ID，不靠猜标题；结果靠回读，不靠“应该成功”。
